# Engrow API — Agent Instructions

FastAPI backend for Engrow (bitácora/tracker de estudio de inglés). SQLAlchemy 2 ORM, Alembic migrations, JWT auth, Google Sign-In, and Web Push.

For setup and running the server, see [LOCAL.md](LOCAL.md) (development) and [PROD.md](PROD.md) (production). Environment variables are documented in [.env.example](.env.example) — don't duplicate that list elsewhere; it drifts.

## Architecture

```
app/
├── main.py            # FastAPI app, middleware, router mounting, startup seeding
├── config.py           # Settings (pydantic-settings, reads .env)
├── database.py         # SQLAlchemy engine, SessionLocal, Base
├── core/
│   ├── security.py     # JWT encode/decode, password hashing
│   ├── dependencies.py # get_current_user, get_db
│   ├── email.py        # Password-reset email sending
│   ├── admin.py        # sqladmin views + auth backend
│   ├── scheduler.py     # APScheduler jobs (sqlite backup, streak-risk push)
│   ├── rate_limit.py    # SlowAPI rate limiting
│   └── seed.py          # Startup DB seeding
├── models/              # SQLAlchemy ORM models — see "Registering a model" below
├── schemas/             # Pydantic request/response schemas, one file per domain
├── routers/             # API endpoints, one file per domain (auth, blocks, plans,
│                         # push, resources, reviews, superadmin, sync, users, writing)
└── __init__.py

alembic/versions/        # Migrations — see "Alembic rules" below
tests/                   # pytest, see conftest.py for the TestClient fixture
```

**Request flow:** router → `Depends(get_current_user)` / `Depends(get_db)` → SQLAlchemy → response schema.

Endpoint reference: run the server and check `/docs` (Swagger) — don't hand-maintain an endpoint list here, it goes stale immediately (there was one in the old AGENTS.md and it was already missing the `/push` routes).

## Registering a model

Every SQLAlchemy model **must** be imported in `app/models/__init__.py`, even if nothing outside `models/` imports it directly. Alembic's `env.py` builds `target_metadata` from `Base.metadata`, which only contains classes that have actually been imported somewhere in the process. Skip the registration and `alembic revision --autogenerate` will conclude the table doesn't belong in the schema and generate a migration that **drops it** — this happened for real with `activity_tips` during this project's push-notifications work.

## Alembic rules

- Never edit a migration file that's already been merged/applied — create a new one.
- Always review the autogenerated diff before running `alembic upgrade head`. Look for unexpected `drop_table`/`drop_column` — usually means a model isn't registered (see above).
- SQLite can't run `ALTER COLUMN` directly. If autogenerate emits `op.alter_column(...)` against an existing SQLite table, wrap it in `with op.batch_alter_table("table_name") as batch_op:` or the migration fails at `alembic upgrade head` with `near "ALTER": syntax error`.

```bash
alembic revision --autogenerate -m "add column xyz"
# review the generated file in alembic/versions/
alembic upgrade head
```

## Authentication

JWT access + refresh tokens (`app/core/security.py`), plus Google Sign-In (`POST /auth/google`, verifies an ID token against `GOOGLE_CLIENT_ID`). Accounts created via Google have `password_hash = NULL` — `login()` explicitly checks for that before calling `verify_password` (a `None` hash would otherwise throw, not just fail auth).

## Web Push

`app/routers/push.py` stores subscriptions (`PushSubscription` model) and sends via `pywebpush`. The `_send()` helper deletes a subscription automatically on a 404/410 response (expired/unsubscribed) — reuse it rather than calling `webpush()` directly. The scheduled job in `app/core/scheduler.py` (`send_streak_risk_pushes`) runs once daily at a fixed server hour, not per-user timezone — a known v1 limitation, not a bug.

## Testing

```bash
pytest
```

Use the `client` fixture from `tests/conftest.py` (spins up a throwaway SQLite DB and overrides `get_db`). Mock external calls at the boundary — see `tests/test_auth_google.py` (mocks `google_id_token.verify_oauth2_token`) and `tests/test_push.py` (mocks `webpush`) for the pattern. Don't hit real Google/FCM endpoints in tests.

## Conventions

- Type hints on every function signature — FastAPI uses them for validation and OpenAPI docs.
- Pydantic schemas: separate read models (with `id`, `created_at`) from write/create models.
- `HTTPException` with the right `status` code for user-facing errors; don't leak internals (see `forgot_password` — email delivery failures are swallowed, not surfaced, to avoid account enumeration).
